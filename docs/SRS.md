## 1. 引言

### 1.1 编写目的

本文档定义 Circo 自我成长周期与成果管理平台的产品范围、用户流程、功能需求、数据需求、非功能需求及验收标准，作为产品设计、技术设计、开发、测试和版本验收的共同依据。

本文档优先描述“系统应提供什么能力”，不限定具体页面样式或 AI 模型实现。

### 1.2 产品愿景

Circo 帮助个人将零散的时间投入、资料阅读、灵感、项目实践和正式成果组织成一个可持续迭代的成长闭环：

```text
Me（认识现状与目标）
  → Find（获取和理解资料）
  → Mind（形成与发展想法）
  → Hand（执行项目并沉淀过程）
  → Land（产出和发布成果）
  → Me（回顾成果、差距与下一周期）
```

系统的核心价值不是单纯保存内容，而是保留内容之间的来源、演化和成果关系，使用户能够回答：

- 我的时间花在了哪里，投入是否有效？
- 一个观点来自哪篇文献或哪次实践？
- 一个灵感如何转化为项目和最终成果？
- 哪些做法带来了成功或错误，下个周期应如何调整？

### 1.3 术语

| 术语 | 定义 |
| --- | --- |
| 周期（Cycle） | 用户设定的一段成长或工作区间，如一周、一个月或一个季度。 |
| 目标（Goal） | 周期内希望达到、可衡量或可判断完成状态的结果。 |
| 文献（Source） | PDF、Markdown 或手动录入的论文、报告、网页摘录等资料。 |
| 灵感（Idea） | 尚未进入正式项目执行阶段的观点、问题、假设或方案。 |
| 项目（Project） | 有目标、计划、进度和过程记录的执行单元。 |
| 成果（Artifact） | 由项目或知识内容转化而来的论文、海报、PPT、博文等正式输出。 |
| 证据（Evidence） | 支持统计、结论、原因分析或成果完成状态的记录、数据和关联内容。 |
| AI 辅助 | 由模型生成翻译、解释、摘要、联想或文稿草案；结果默认是建议，不视为已核实事实。 |

## 2. 总体描述

### 2.1 用户与使用场景

MVP 面向单一用户，主要使用者包括科研人员、学生、知识工作者和独立创作者。典型场景如下：

1. 用户建立月度周期，设定研究目标和目标工时。
2. 用户记录工作计时，并在任务完成后标记产出、成功或错误原因。
3. 用户导入 PDF，转换为 Markdown，阅读翻译、解释和摘要。
4. 用户把文献观点发展成灵感，再将成熟灵感转成项目。
5. 用户为项目维护计划、日志和实验数据。
6. 用户将项目内容生成论文、海报或博文草稿，并追踪发布状态。
7. 周期结束时，系统汇总投入、成果、目标差距和经验，辅助用户制定下一周期。

### 2.2 产品原则

- **本地优先**：核心数据默认保存在用户本地，基本记录和检索不依赖外部服务。
- **来源可追溯**：AI 结论、灵感、项目和成果应尽可能关联其原始文献或过程证据。
- **用户最终控制**：所有 AI 结果均可编辑、重新生成、接受或废弃，未经确认不得覆盖原文。
- **闭环而非孤岛**：五个模块共享标签、搜索和关联关系。
- **渐进式结构化**：允许先快速记录，再补充标签、原因、项目等结构化信息。

### 2.3 运行边界与假设

- MVP 为桌面端优先的响应式 Web 应用，采用单用户、无账号模式。
- 核心数据存储于本地 SQLite；大型附件保存在本地文件存储中，数据库记录元数据和路径。
- PDF 文本提取质量受扫描件、公式、表格和排版影响。OCR、复杂公式恢复及版面完全还原不属于 MVP 必达范围。
- 翻译、解释、摘要和内容生成需要配置可用的 AI 服务；未配置或服务不可用时，非 AI 功能仍应正常使用。
- 音视频在 MVP 中以附件形式管理，不要求自动转写、剪辑或内容理解。

### 2.4 版本优先级

需求使用以下优先级：

- **P0**：MVP 必须具备，否则无法形成基本成长闭环。
- **P1**：首个正式版本需要，MVP 可采用简化实现。
- **P2**：后续增强能力。

## 3. 核心信息架构与业务流程

### 3.1 一级模块

| 模块 | 主要职责 | 关键输入 | 关键输出 |
| --- | --- | --- | --- |
| Me | 周期、目标、投入和复盘 | 工时、目标、事件、原因 | 效率指标、成就、差距、复盘 |
| Find | 文献导入、阅读和评价 | PDF、Markdown、笔记 | 可检索文本、导读、标记、摘要 |
| Mind | 灵感捕获和系统化推演 | 自由记录、文献观点、项目问题 | 灵感卡片、推演分支、候选项目 |
| Hand | 项目执行和过程沉淀 | 灵感、计划、任务、日志、数据 | 进度、过程证据、阶段结论 |
| Land | 正式成果生产与管理 | 文献、灵感、项目材料 | 论文、PPT、海报、文案、博文 |

### 3.2 主流程

#### 流程 A：成长周期闭环

1. 创建周期并设置一个或多个目标及衡量方式。
2. 记录工作会话，将时间关联到目标、项目或任务。
3. 在周期内持续沉淀文献、灵感、项目日志和成果。
4. 系统按目标汇总投入、进度、成果及成功/错误原因。
5. 用户完成复盘，选择经验并创建下一周期目标。

#### 流程 B：知识到成果

1. 导入文献并完成文本转换。
2. 对文献进行导读、标记和总结，生成可引用的阅读笔记。
3. 从文献段落或总结创建灵感，并记录来源。
4. 将灵感转化为项目，维护计划、任务、日志和数据。
5. 从项目生成正式成果草稿，编辑、导出并记录发布信息。

### 4.2 Me 模块：自我数据统计

#### 4.2.1 周期与目标

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| ME-001 | P0 | 用户应能创建、编辑、归档周期，并设置名称、起止日期和复盘频率。 |
| ME-002 | P0 | 用户应能在周期中创建目标，设置描述、目标值、单位、截止日期及优先级。 |
| ME-003 | P0 | 目标应支持定量衡量（如 40 小时、完成 3 篇）和定性判断（未开始/进行中/已完成）。 |
| ME-004 | P0 | 用户应能手动更新目标进度，也能选择由关联任务或成果自动汇总。 |
| ME-005 | P1 | 用户应能将未完成目标及复盘结论复制到下一周期。 |

#### 4.2.2 工时与效率

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| ME-010 | P0 | 用户应能通过开始/暂停/结束计时器记录工作会话。 |
| ME-011 | P0 | 用户应能手动补录、修改工作会话，字段至少包括开始时间、结束时间、时长、事项和备注。 |
| ME-012 | P0 | 工作会话应可关联周期、目标、项目和任务。 |
| ME-013 | P0 | 系统应按日、周、月、周期、项目和目标统计工作时长。 |
| ME-014 | P0 | 用户应能在工作会话结束后记录产出数量、完成程度和专注度。 |
| ME-015 | P0 | 系统应展示效率指标的计算口径，不得只显示无定义的综合分数。 |
| ME-016 | P0 | MVP 应至少提供“有效投入率 = 标记为有效的工作时长 / 总工作时长”和“计划完成率 = 已完成任务数 / 到期计划任务数”；分母为 0 时显示“暂无数据”。 |
| ME-017 | P1 | 用户应能自定义效率指标名称、公式所用字段和目标阈值。 |

| 编号 | 优先级 | 需求 |
| --- | --- | --- |

| ME-025 | P1 | 系统应按周期比较工时、效率、完成率、原因分类和成果数量的变化趋势。 |
| ME-026 | P1 | 周期结束时，系统应生成包含数据摘要、成功经验、错误原因、未达目标和下一步行动的复盘草稿。 |

## 5. AI 辅助功能要求

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| AI-001 | P0 | AI 服务配置应与业务数据分离，密钥不得以明文展示在界面或日志中。 |
| AI-002 | P0 | 发起 AI 请求前，系统应让用户知道将发送的内容范围；默认只发送完成任务所需的最小内容。 |
| AI-003 | P0 | AI 任务应显示排队、处理中、成功、失败或已取消状态，且不得阻塞其他非 AI 操作。 |
| AI-004 | P0 | AI 请求失败时应保留用户输入，并提供错误说明和重试入口。 |
| AI-005 | P0 | AI 生成结果不得自动覆盖用户原文，也不得未经确认自动发布或标记为事实。 |
| AI-006 | P0 | 支持引用来源的任务应保留来源定位；没有足够材料时应提示信息不足。 |
| AI-007 | P1 | 用户应能选择生成语言、详细程度和目标读者。 |
| AI-008 | P1 | 系统应允许用户查看和删除本地保存的 AI 任务记录。 |

## 6. 数据需求

### 6.1 核心实体

| 实体 | 关键字段 | 主要关系 |
| --- | --- | --- |
| Cycle | 名称、起止日期、状态、复盘 | 包含 Goal、WorkSession、Review |
| Goal | 描述、衡量类型、目标值、当前值、单位、状态 | 属于 Cycle；关联 Project、Artifact |
| WorkSession | 起止时间、时长、事项、有效性、专注度、产出 | 关联 Goal、Project、Task |
| EventReason | 类型、现象、原因、影响、证据、改进 | 关联 Cycle、Project、WorkSession |
| Source | 元数据、文件路径、转换文本、阅读状态 | 包含 Annotation、Summary；关联 Idea |
| Annotation | 原文定位、内容、标记类型、理由 | 属于 Source |
| Idea | 内容、状态、评价、推演类型 | 来源于 Source/Idea；转化为 Project |
| Project | 目的、预期成果、时间、状态 | 包含 Task、Log、Attachment；产出 Artifact |
| Task | 标题、层级、计划/实际时间、状态 | 属于 Project；关联 WorkSession |
| ProjectLog | 时间、类型、正文、下一步 | 属于 Project；关联 Task、Source、Idea |
| Attachment | 文件元数据、路径、说明、校验信息 | 关联 Project、Log、Artifact |
| Artifact | 类型、结构、正文、状态、发布信息 | 来源于 Project、Source、Idea、Log |
| AIJob | 任务类型、输入引用、输出、状态、服务标识 | 关联 Source、Idea、Project 或 Artifact |

### 6.2 数据关系规则

- 每条跨模块关系应记录关系类型、创建时间和创建方式（用户创建/系统建议）。
- 删除被引用实体时，系统应提示影响范围；默认保留关系占位信息，不级联删除成果或日志。
- 文件应使用稳定标识关联，不应仅依赖用户可修改的显示名称。
- 统计值应能够追溯到原始工作会话、任务、目标或成果。

### 6.3 数据导入、导出与备份

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| DATA-001 | P0 | 用户应能导出全部结构化业务数据为 JSON，并包含数据版本号。 |
| DATA-002 | P0 | 用户应能创建包含数据库和附件的完整本地备份。 |
| DATA-003 | P0 | 系统应能从兼容备份恢复；恢复前应校验备份完整性并提示覆盖影响。 |
| DATA-004 | P1 | 系统应支持导入标准 Markdown、CSV 任务/工时数据。 |
| DATA-005 | P1 | 系统应提供自动备份频率和保留数量设置。 |

## 7. 外部接口需求

### 7.1 用户界面

- 桌面端应支持最新稳定版 Chrome、Edge 和 Safari。
- 首页应展示当前周期目标、今日/本周投入、进行中项目、待处理文献/灵感和近期成果。
- 所有关键状态不得仅以颜色表达，应同时使用文字或图标。
- 长时间任务应展示进度或明确的处理中状态。
- 表单在离开未保存页面前应提示用户。

### 7.2 文件接口

- 输入：PDF、MD、TXT、CSV、JSON，以及常见图片、音频和视频格式。
- MVP 输出：JSON 备份、Markdown、PDF；其他格式按 Land 需求逐步扩展。
- 单文件大小上限应可配置，超过限制时应在上传前或上传开始时明确提示。

### 7.3 外部服务接口

- AI 服务应通过可替换的适配层接入，业务模块不得绑定单一供应商。
- 外部请求应设置超时、失败重试上限和取消能力。
- 若后续接入发布平台，发布行为必须由用户明确触发和确认。

### 8.2 可靠性与完整性

| NFR-REL-003 | 附件应支持完整性校验；数据库记录与文件不一致时应可检测并报告。 |
| NFR-REL-004 | 数据库结构升级前应创建可恢复备份，并提供迁移失败处理。 |

| 编号 | 需求 |
| --- | --- |

## 9. MVP 范围

### 9.1 MVP 包含

- 单用户、本地 SQLite 数据存储。
- 周期、目标、计时、基础效率统计、原因记录、目标差距和成就视图。
- PDF/Markdown 导入、基础 PDF 转 Markdown、原文定位、翻译/解释/总结、正反例标记。
- 灵感快速记录、七类推演方式、评价、来源关联和转项目。
- 项目、任务、里程碑、日志及多类型附件管理。
- 论文、海报、PPT 大纲、自媒体文案和博文的模板化草稿、编辑和基础导出。
- 跨模块关联、统一检索、JSON 导出及完整备份。

### 9.2 MVP 不包含

- 多用户、团队协作、权限管理和云端实时同步。
- 自动发表论文或自动发布到第三方内容平台。
- 扫描件高精度 OCR、复杂数学公式和复杂表格的完全还原。
- 音视频自动转写、剪辑或语义分析。
- 对 AI 输出真实性、新颖性、学术正确性或查重结果作保证。
- 完整的 DOCX/PPTX 专业排版能力。

## 10. 验收标准

### 10.1 端到端验收场景

#### AC-E2E-01：完成一次成长周期

**给定**用户创建一个 7 天周期、一个 10 小时目标和一个项目；  
**当**用户记录至少 3 次工作会话、完成 2 个任务、记录 1 条成功原因和 1 条错误原因；  
**则**系统应正确显示总工时、有效投入率、任务完成率、目标差距和原因分类，并能生成可编辑的周期复盘草稿。

#### AC-E2E-02：从文献形成项目

**给定**用户导入一份含可提取文本的 PDF；  
**当**系统完成 Markdown 转换，用户对一个段落进行翻译、解释和正例标记，再由该段落创建灵感并转为项目；  
**则**项目应能反向追溯到灵感、标记、原文段落和 PDF 页码。

#### AC-E2E-03：从项目形成成果

**给定**项目中已有计划、日志、数据附件和关联文献；  
**当**用户创建“博文”成果并选择上述材料生成草稿；  
**则**系统应展示使用的材料范围，生成可编辑内容，保留来源关联，允许导出 Markdown，并在成果定稿后计入 Me 成就。

#### AC-E2E-04：AI 服务不可用

**给定**AI 服务未配置或请求失败；  
**当**用户继续记录工时、编辑文献 Markdown、创建灵感和维护项目；  
**则**非 AI 功能应保持可用，AI 任务应显示明确错误且可重试，用户输入不得丢失。

#### AC-E2E-05：备份与恢复

**给定**系统中存在至少一个周期、文献、灵感、项目、附件和成果；  
**当**用户创建完整备份并在兼容环境中恢复；  
**则**实体内容、状态、附件及跨模块关系应保持一致，统计结果应可重新计算得到相同值。

### 10.2 MVP 完成定义

MVP 只有在以下条件全部满足时方可验收：

1. 所有 P0 需求已实现，或经评审形成明确的范围变更记录。
2. 五个端到端验收场景全部通过。
3. 核心数据具备备份与恢复能力，无已知的数据丢失级缺陷。
4. 效率、目标差距和成就统计能够追溯到原始记录。
5. AI 生成内容与用户内容在界面和数据中可区分，并保留必要来源。

## 11. 约束、风险与待确认事项

### 11.1 主要风险

| 风险 | 影响 | 应对方向 |
| --- | --- | --- |
| “工作效率”定义因用户而异 | 指标失真或引导错误行为 | MVP 提供透明的基础指标，后续允许自定义，不使用黑箱总分。 |
| MinerU 缺失、模型未下载或转换失败 | 文献 Markdown 不可用 | 保存原 PDF、显示明确错误、允许安装模型后重试。 |
| AI 幻觉或错误引用 | 学术与内容可信度风险 | 强制来源提示、待核实标记和用户确认，不自动发布。 |
| 模块过多导致操作负担 | 用户难以持续记录 | 支持快速记录、渐进补全和跨模块复用。 |
| 本地文件迁移或丢失 | 附件不可用 | 完整备份、校验、异常检测和稳定文件标识。 |

### 11.2 产品评审待确认

以下事项不阻碍 MVP 原型启动，但应在详细设计阶段确认：

1. 成长周期采用日、周、月、年由用户首次启动时选择。
2. 效率指标是否需要引入主观“质量评分”，以及评分量表。
3. 首批接入的 AI 服务、隐私策略、调用成本上限和离线替代方案。
4. PDF 转换对公式、表格、双栏论文和中文扫描件的最低质量要求。
5. Land 首个重点成果类型是论文、PPT 还是博文，以决定模板和导出优先级。
6. 附件单文件上限、备份位置和自动备份策略。
