| 项目 | 内容 |
| --- | --- |
| 文档版本 | v1.0 |
| 适用产品 | Circo 自我成长周期与成果管理平台 |
| 适用阶段 | 架构设计、UI 设计、开发、代码评审、测试与验收 |
| 编制日期 | 2026-08-11 |
| 约束等级 | 必须遵守；例外须记录并经项目负责人确认 |

## 1. 文档目的

本文档规定 Circo 的代码组织、软件架构、界面风格、主题、国际化、颜色、CSS 和图标使用要求。所有新增代码、重构代码和 UI 组件均应符合本规范。

本文档中的关键词含义如下：

- **必须**：不可省略的验收条件。
- **应当**：原则上必须遵守，偏离时需要说明原因。
- **可以**：根据实际场景选择。

若本文档与软件需求规格说明书冲突，应先确认产品需求，再更新相应文档，禁止仅在代码中形成隐含规则。

## 2. 技术基线

| 开发语言 | TypeScript，开启严格类型检查 |
| UI 框架 | React |

| 图标 | Heroicons |
| 软件架构 | MVVM Architecture |
| 数据存储 | 本地 SQLite |

## 3. 强制代码规模要求

### 3.1 单文件不超过 300 行

1. 项目内由团队维护的源代码文件，每个文件最多 **300 个物理行**。
2. 行数统计包含空行、注释、导入、类型定义和代码行。
3. 适用文件至少包括 `.ts`、`.tsx`、`.js`、`.jsx`、`.css`、`.mjs` 和项目维护的脚本文件。
4. 自动生成文件、依赖锁文件、数据库迁移快照和第三方代码可以例外，但必须能够明确识别为生成或外部文件，不得手工堆积业务逻辑。
5. 文档、数据样例和配置文件不受 300 行硬限制，但应保持可读并按主题拆分。
6. 不得通过压缩代码、合并多条语句、删除必要空行或减少可读性来规避限制。
7. 文件预计超过 240 行时应主动评估拆分，避免在达到 300 行后仓促处理。
8. 代码评审和持续集成必须检查文件行数；超过限制的受控源文件不得合并。

### 3.2 文件拆分原则

文件接近上限时，应按职责拆分，而不是机械地按行切割：

- UI 展示拆分为独立组件。
- 状态与交互拆分为 ViewModel 或自定义 Hook。
- 业务规则拆分为 Use Case、Domain Service 或纯函数。
- 数据读写拆分为 Repository。
- 类型和接口按业务域放置，避免建立无边界的全局类型文件。
- 文案进入国际化资源文件，不直接堆积在组件中。
- 通用常量和设计令牌进入对应的配置模块。

## 4. 高内聚、低耦合要求

### 4.1 高内聚

- 每个文件、类、函数和组件必须有单一、清晰的主要职责。
- 同一业务能力的数据、规则和操作应组织在同一业务模块内。
- ViewModel 应围绕一个页面或一个明确的交互场景组织，不得成为全局状态垃圾桶。
- Repository 应围绕业务实体提供数据能力，不得暴露数据库实现细节给 View。
- 组件的名称、输入和输出必须能够表达其业务目的。

### 4.2 低耦合

- 模块之间必须通过公开接口、类型或事件协作，不得访问其他模块的内部文件。
- View 不得直接访问数据库、文件系统、第三方 AI SDK 或底层网络客户端。
- Domain 与 Use Case 不得依赖 React、Next.js 页面组件或具体数据库驱动。
- 外部 AI、文件转换、导出和存储能力必须通过适配器接口接入，以便替换实现。
- 禁止循环依赖。
- 禁止依赖组件内部状态、DOM 结构或未声明的全局变量完成跨模块通信。
- 共享模块只保存真正跨领域的基础能力；不得把业务代码放入 `utils` 形成隐性耦合。

### 4.3 依赖方向

推荐依赖方向如下：

```text
View → ViewModel → Use Case / Domain ← Repository Interface
                                      ↑
                            Infrastructure Adapter
```

外层可以依赖内层定义的接口，内层不得反向依赖外层实现。

## 5. MVVM Architecture

### 5.1 Model

Model 负责业务数据和业务规则，包括：

- 领域实体和值对象。
- 数据校验与状态转换规则。
- Use Case / Application Service。
- Repository 接口。
- 与 UI 无关的统计、转换和计算逻辑。

Model 不得：

- 返回 JSX。
- 读取或修改 DOM。
- 依赖页面路由或 React 组件状态。
- 将 SQLite 行结构直接作为所有上层的业务模型。

### 5.2 View

View 负责视觉呈现和收集用户输入，包括：

- Next.js 页面和布局。
- React 展示组件。
- Tailwind 样式。
- 无障碍属性和响应式布局。
- 将用户事件交给 ViewModel。

View 必须尽量保持声明式。除局部纯视觉状态外，不应承载业务流程、复杂数据转换或持久化逻辑。

### 5.3 ViewModel

ViewModel 负责连接 View 与 Model，包括：

- 页面所需数据的组合和展示状态。
- 加载、空白、错误、成功等状态。
- 表单状态、输入校验和用户操作编排。
- 调用 Use Case，并将结果转换为 View 可直接消费的数据。
- 对 View 暴露稳定、语义清晰的状态和命令。

在 React 中，ViewModel 可以实现为自定义 Hook 或不依赖 JSX 的 TypeScript 模块。命名建议采用 `useXxxViewModel.ts` 或 `xxx-view-model.ts`。

ViewModel 不得包含 JSX、Tailwind 类名或具体数据库查询语句。

### 5.4 Infrastructure

虽然 Infrastructure 不属于 MVVM 三个核心角色，但项目必须设置基础设施层承载：

- SQLite Repository 实现。
- 文件系统访问。
- PDF 转换。
- AI 服务适配器。
- 导入、导出与备份实现。
- 日志和外部服务客户端。

### 5.5 推荐目录结构

具体目录应以当前 Next.js 版本要求为准，业务代码推荐采用以下结构：

```text
src/
  app/                       # 路由、页面、布局与服务端入口
  modules/
    me/
      model/                 # 实体、规则、接口
      use-cases/             # 应用用例
      view-models/           # 页面状态与操作编排
      views/                 # 模块页面及业务组件
      infrastructure/        # 本模块的数据适配器
    find/
    mind/
    hand/
    land/
  shared/
    components/              # 跨模块基础 UI
    i18n/                    # 国际化基础设施
    theme/                   # 主题与设计令牌
    icons/                   # Heroicons 封装
    infrastructure/          # 跨模块基础设施
```

模块私有组件必须放在模块内；只有被多个模块稳定复用的组件才能提升到 `shared`。

## 6. 极简黑白视觉规范

### 6.1 基本原则

- 产品界面必须采用极简风格，突出内容和任务本身。
- 常规界面只使用黑、白以及两者之间的中性灰阶。
- 禁止使用渐变、霓虹、拟物高光、无业务意义的大面积阴影或装饰性色块。
- 通过字号、字重、间距、边框、明暗对比和布局层级表达信息结构。
- 动画必须克制，只用于状态变化、反馈和空间关系说明。

### 6.2 中性色使用

允许使用 Tailwind 的中性灰阶，例如 `black`、`white`、`zinc-*`。项目应统一选择一套中性色阶，不得在同一界面混用 `gray`、`slate`、`neutral`、`stone` 等多套灰阶造成视觉漂移。

建议使用 `zinc` 作为默认中性色：

| 用途 | 白天模式 | 夜间模式 |
| --- | --- | --- |
| 页面背景 | `white` / `zinc-50` | `black` / `zinc-950` |
| 主要文字 | `zinc-950` | `zinc-50` |
| 次要文字 | `zinc-600` | `zinc-400` |
| 边框 | `zinc-200` | `zinc-800` |
| 次级表面 | `zinc-50` | `zinc-900` |
| 禁用状态 | `zinc-400` | `zinc-600` |

颜色必须通过统一设计令牌或共享组件使用。禁止在业务页面随意创造近似颜色。

## 7. 白天与夜间模式

### 7.1 功能要求

- 系统必须支持白天模式和夜间模式切换。
- 应支持“跟随系统”“白天”“夜间”三个选项。
- 用户选择必须持久化，刷新页面和重新启动应用后仍然有效。
- 首次访问且未保存选择时，应跟随操作系统主题。
- 主题初始化不得出现明显的错误主题闪烁。
- 所有页面、弹窗、图表、编辑器、表单、代码块和状态色都必须适配两种模式。

### 7.2 实现要求

- 主题应通过根元素的类或标准主题机制控制。
- Tailwind 样式应使用项目统一的暗色模式方案。
- 禁止在组件中根据主题复制两套业务结构。
- 图标默认继承当前文字颜色。
- 两种主题下的正文、交互控件和状态提示均应满足 WCAG 2.2 AA 对比度要求。

## 8. 中英文切换

### 8.1 功能要求

- 系统必须支持简体中文 `zh-CN` 和英文 `en`。
- 用户可在界面中随时切换语言，切换后当前上下文应保持不变。
- 语言选择必须持久化；首次使用可根据系统语言选择，无法匹配时默认简体中文。
- 页面标题、导航、按钮、表单标签、校验错误、空状态、通知、状态名称和无障碍文本均必须国际化。
- 日期、时间、数字和复数表达必须按当前语言环境格式化。
- 用户输入、文献原文、项目数据和 AI 生成内容不得因切换界面语言被自动改写。

### 8.2 开发要求

- 禁止在 View 和 ViewModel 中硬编码面向用户的中英文文案。
- 所有界面文案必须使用稳定的语义键，不得以中文或英文原句作为键。
- 中英文资源文件的键必须保持一致，持续集成应检查缺失键。
- 拼接式翻译应尽量避免，应使用带变量的完整句子模板。
- 布局必须允许英文文案比中文更长；不得依靠固定宽度截断关键操作文字。
- 新增功能必须同时提交中英文文案后方可验收。

## 9. 状态指示色规范

### 9.1 允许范围

红、黄、绿、蓝仅用于表达状态、风险、反馈或需要特别识别的信息，不得作为常规品牌色或大面积装饰色。

| 颜色 | 语义 | 典型用途 |
| --- | --- | --- |
| 红 | 错误、危险、失败、严重逾期 | 删除警告、保存失败、严重风险 |
| 黄 | 警告、等待、注意、存在风险 | 即将逾期、待核实、处理中 |
| 绿 | 成功、完成、正常 | 操作成功、目标完成、服务正常 |
| 蓝 | 信息、进行中、中性提示 | 信息说明、当前步骤、同步中 |

### 9.2 使用要求

- 状态色必须采用 Tailwind 标准色阶，并在共享状态组件中统一封装。
- 同一状态在不同页面必须使用相同颜色语义。
- 状态不得只依赖颜色区分，必须同时提供文字、图标、形状或辅助说明。
- 状态色应优先用于小面积元素，如图标、圆点、徽标、左边框或浅色提示背景。
- 夜间模式必须使用适合暗色背景的色阶，不能简单沿用白天模式色值。
- 红色只用于真实危险或错误，不得用于普通取消按钮或吸引点击。
- 正例与反例可分别使用绿色与红色，但必须同时显示“正例/Positive”或“反例/Negative”文本。

## 10. Tailwind CSS 要求

1. 所有新 UI 样式必须优先使用 Tailwind CSS。
2. 全局 CSS 仅用于 Tailwind 初始化、全局设计令牌、浏览器标准化和确实无法通过工具类合理实现的基础规则。
3. 禁止引入另一套通用 CSS 框架与 Tailwind 并存。
4. 禁止在 JSX 中大量使用内联 `style`；只有运行时计算且 Tailwind 无法表达的值可以例外。
5. 重复出现的样式组合应提取为共享组件或受控的样式变体，不得复制超长类名到多个页面。
6. Tailwind 类名必须可静态识别；不得通过不可枚举的字符串拼接动态生成类名。
7. 响应式、暗色、焦点、禁用和状态样式必须与组件一起实现。
8. 自定义任意值应谨慎使用；相同任意值重复出现时必须提升为设计令牌。
9. 类名组织应保持一致，建议顺序为布局、尺寸、间距、排版、颜色、边框、效果和状态变体。

## 11. Heroicons 要求

1. 必要的功能标志和操作图标必须使用 Heroicons。
2. 不得同时引入其他通用图标库，避免风格不一致和增加包体积。
3. 同一产品区域应统一使用 Outline 或 Solid 风格：默认操作使用 Outline，选中或明确状态可以使用 Solid。
4. 常规图标尺寸应采用统一规格，例如 16、20、24 像素。
5. 图标颜色默认继承文字颜色；状态图标可以使用规定的红、黄、绿、蓝状态色。
6. 纯装饰图标必须对辅助技术隐藏。
7. 只有图标而没有可见文字的按钮，必须提供可访问名称和悬浮提示。
8. 禁止使用 Emoji、文字字符或自行绘制的近似图标代替已有 Heroicon。
9. 若 Heroicons 确实没有所需业务图标，可以使用文字标识或经评审的自定义 SVG；自定义 SVG 必须遵循相同尺寸、线宽和颜色规则。

## 12. 组件设计要求

- 基础组件至少应包括 Button、IconButton、Input、Select、Textarea、Dialog、Dropdown、Tabs、Badge、Alert、Tooltip、EmptyState 和 LoadingState。
- 基础组件必须统一处理尺寸、焦点、禁用、错误、明暗主题和可访问性。
- 业务组件不得绕过基础组件重复实现按钮、弹窗或状态徽标。
- 组件 Props 应保持最小、明确，不得传入整个页面对象只为读取少数字段。
- 布尔 Props 应表达清晰状态，复杂模式优先使用语义明确的枚举。
- 展示组件应尽可能无副作用，并能通过输入数据独立测试。
- 列表必须提供加载、空白、错误和正常四种状态。
- 会导致数据丢失的操作必须二次确认；普通可撤销操作不应滥用确认弹窗。

## 13. TypeScript 与质量要求

- 禁止新增无说明的 `any`；外部输入必须先作为 `unknown` 校验再使用。
- 领域状态应使用明确联合类型或枚举，禁止依赖任意字符串。
- 函数参数和返回值必须具有可理解的类型边界。
- 业务计算应优先实现为无副作用的纯函数。
- 错误不得静默吞掉；应转换为用户可理解的状态，并保留必要的诊断信息。
- 日志不得包含 API 密钥、完整私密文献内容或用户敏感数据。
- 禁止保留无引用死代码、大段注释掉的代码和无责任人的 TODO。
- 每次提交必须通过格式检查、静态检查、类型检查和相关测试。

## 14. 测试要求

### 14.1 必测内容

- Model 中的业务规则、效率公式和状态转换必须具有单元测试。
- ViewModel 必须测试加载、成功、空白、错误及主要用户操作。
- Repository 必须测试数据写入、查询、事务和异常处理。
- 主题切换必须测试持久化、系统主题回退和首次渲染。
- 国际化必须测试中英文资源键一致性及关键页面无硬编码文案。
- 状态组件必须测试文字/图标与颜色语义一致，且不只依赖颜色。
- 五模块核心闭环必须具有端到端测试。

### 14.2 UI 验收矩阵

所有核心页面至少覆盖以下组合：

| 语言 | 白天模式 | 夜间模式 |
| --- | --- | --- |
| 简体中文 | 必测 | 必测 |
| 英文 | 必测 | 必测 |

每种组合都应检查布局溢出、颜色对比度、图标、状态反馈和键盘操作。

## 15. 代码评审检查清单

每个合并请求必须确认：

- [ ] 所有受控源文件不超过 300 行。
- [ ] 文件和模块职责单一，没有可识别的循环依赖。
- [ ] 依赖方向符合 MVVM，View 未直接访问数据源或外部服务。
- [ ] 新增 UI 使用 Tailwind，未引入第二套 CSS 框架。
- [ ] 常规界面只使用黑白灰，彩色仅表达规定状态。
- [ ] 白天和夜间模式下均可读、可操作，无主题闪烁问题。
- [ ] 所有用户可见文案均提供中文和英文资源。
- [ ] 必要图标来自 Heroicons，图标按钮具备可访问名称。
- [ ] 加载、空白、错误、成功和禁用状态完整。
- [ ] 新增业务规则、ViewModel 和关键交互具有相应测试。
- [ ] 未引入敏感信息、死代码或未经说明的 `any`。
- [ ] 当前 Next.js API 用法已依据项目内对应版本文档核对。

## 16. 自动化门禁要求

持续集成至少必须执行以下检查：

1. 文件行数检查：受控源文件不得超过 300 行。
2. ESLint 检查。
3. TypeScript 类型检查。
4. 单元测试和关键集成测试。
5. 中英文翻译键一致性检查。
6. 生产构建检查。
7. 循环依赖检查。

任一强制检查失败时不得合并。自动生成文件例外清单必须显式维护，不得使用宽泛目录规则跳过手写业务代码。

## 17. 完成定义（Definition of Done）

一项功能只有同时满足以下条件才视为开发完成：

1. 功能符合 SRS 及对应验收标准。
2. 代码符合 MVVM、高内聚、低耦合和 300 行限制。
3. 页面符合黑白极简风格，状态色使用正确。
4. 白天与夜间模式均完成适配。
5. 简体中文与英文均完成适配。
6. 图标使用 Heroicons 并满足可访问性要求。
7. 相关自动化测试已添加并通过。
8. 静态检查、类型检查和生产构建通过。
9. 必要的开发文档、数据迁移和变更说明已更新。
